# Life Analytics (LifeOS)

Personal life-analytics app — expenses/budgeting first, later subscriptions, habits, sleep, productivity, etc. Currently at **Milestone 1: technical foundation only**. No real data model yet — it will be designed once the user's existing expense-tracking spreadsheets are reviewed. Do not invent schema, categories, or fake data ahead of that.

## Stack

Next.js (App Router) + TypeScript + Tailwind CSS v4 + Prisma 7 (driver adapters) + Supabase Postgres. Deploys to Vercel.

## Commands

```bash
npm run dev         # start dev server
npm run build       # production build (also type-checks)
npm run lint        # ESLint
npm test            # Vitest unit tests for the pure lib modules (src/**/*.test.ts; npm run test:watch)
npx prisma generate # regenerate Prisma Client (also runs automatically via postinstall)
npm run db:push     # push prisma/schema.prisma to Supabase (no migration history yet) — ALSO run against the cat deployment, see below
npx tsx prisma/apply-checks.ts  # after db:push: locks out Supabase's API (RLS + revoked grants) and adds CHECK constraints db push can't express (idempotent; --dry only reports)
npm run db:check    # read-only: do your DB and the cat one (CAT_DIRECT_URL) match schema.prisma + apply-checks? exit 1 on drift
npm run db:studio   # Prisma Studio
```

## Second deployment (cat theme) — schema changes go to BOTH databases

The same repo also runs a second, separate copy for someone else: its own Vercel project (`NEXT_PUBLIC_THEME=cat`) and its own Supabase project (ref `ipcjkxtwyiumfvijxmsg`, eu-central-1; the user's own is `vmqptzdzukenkwauunex`). Every push to `main` deploys both, but **database changes don't**. Whenever `prisma/schema.prisma`, `prisma/apply-checks.ts` or `prisma/checks.ts` changes, **remind the user** that after doing their own database, they also need to run against the cat one:

1. In `.env`, comment out their own `DATABASE_URL`/`DIRECT_URL` and uncomment the cat project's lines.
2. `npm run db:push` then `npx tsx prisma/apply-checks.ts`.
3. Switch `.env` back (otherwise local dev reads/writes the other person's data).
4. `npm run db:check` — confirms both databases match (needs `CAT_DIRECT_URL` in `.env`: the cat project's direct URL, read only by this check).

Do this before (or right when) pushing the code, or the cat site breaks on the new schema. Never run the one-off `prisma/import-*`/`label-periods` scripts against it — those load the user's own data.

## Environment

`.env` (gitignored, never commit) needs two Supabase connection strings — see `.env.example`:
- `DATABASE_URL` — pooled (pgbouncer, port 6543). Used by the app at runtime.
- `DIRECT_URL` — direct (port 5432). Used only by Prisma CLI commands (push/migrate/studio) — DDL isn't reliable through pgbouncer.
- `CAT_DIRECT_URL` — optional, the cat deployment's direct URL; only `npm run db:check` (`prisma/check-drift.ts`) reads it.
- `SPOONACULAR_API_KEY` — server-only, for the /recipes deck. Free tier ≈150 points/day; one deck batch (10 recipes) costs ~1.6.
- `APP_PASSWORD` + `AUTH_SECRET` — the single-user passcode gate (`APP_PASSWORD` = 4–8 digits). Without `APP_PASSWORD` the gate is off in development and everything is locked in production.
- `NEXT_PUBLIC_VAPID_PUBLIC_KEY` + `VAPID_PRIVATE_KEY` (+ optional `VAPID_SUBJECT`) — Web Push keys (`npx web-push generate-vapid-keys`); without them push is off. Both deployments use the same VAPID values (the public key is config, not a secret; `NEXT_PUBLIC_` is inlined at build, so redeploy after changing it). `CRON_SECRET` — bearer token for `/api/push/cron`, different per deployment (the cat one is kept as a comment in `.env`). See "Push scheduler" below.
- `NEXT_PUBLIC_THEME` — unset = green sheep (Meadow). `cat` = pink with a cat, for a second copy of the app (another Vercel project + Supabase on the same repo). Build-time: `src/lib/theme.ts` sets `data-theme` on `<html>` (pink tokens in `globals.css`), `<Sheep>` renders `<Cat>`, and loading phrases, fun facts and "tap the sheep" copy follow. App icons come from `THEME_ICONS` (all in `public/`: `icon-cat*.png`/`icon-cat.svg`/`apple-icon-cat.png`, made from `Cat.tsx`); `offline.html` and `global-error.tsx` stay sheep/green.

## Push scheduler (GitHub Actions)

Vercel only runs code on a request (and Hobby crons are daily), so `.github/workflows/push-cron.yml` calls `GET <site>/api/push/cron` with `Authorization: Bearer <CRON_SECRET>` every 15 minutes (GitHub may run it a few minutes late), once per deployment. It needs four repository secrets (Settings → Secrets and variables → Actions):

- `LIFEOS_URL` / `LIFEOS_CRON_SECRET` — the user's site (its own `https://<project>.vercel.app`, no path) and that Vercel project's `CRON_SECRET`.
- `CAT_URL` / `CAT_CRON_SECRET` — the same for the cat deployment. A step whose URL secret is empty is skipped.

Each step prints `HTTP <code>` and the reply and fails on anything but 200: `{"devices":N,"sent":[…],"failed":[…]}` is healthy (`devices` = subscribed phones; `failed` = `<sub>:<kind>` that threw this run, logged in Vercel and retried next run); a 307 to `/login` means the deployed code has no `/api/push/cron` yet (still deploying); another 3xx means a redirecting URL secret; 401 means the secret doesn't match Vercel's. Test by hand with Actions → Push notifications → Run workflow. The repo is public, so Actions minutes are free, but GitHub disables scheduled workflows after 60 days without commits; the keepalive job in `backup.yml` prevents that (else re-enable on the workflow page). Git on this machine may be logged in as another GitHub account without push rights; the user pushes themselves.

## Backups

`.github/workflows/backup.yml` runs every Sunday 02:26 UTC (and by hand): `pg_dump --schema=public` of both databases, restores each into a throwaway Postgres 17 (fails if it doesn't load, logs a few row counts), encrypts with `gpg --symmetric` and commits `own/<date>.sql.gz.gpg` / `cat/<date>.sql.gz.gpg` to a separate **private** repo (this repo is public, so no artifacts here). Secrets: `BACKUP_REPO`, `BACKUP_DEPLOY_KEY` (write deploy key on that repo), `BACKUP_PASSPHRASE` (also kept in a password manager), `OWN_DATABASE_URL` / `CAT_DATABASE_URL` (the direct session-pooler URLs, IPv4). Restore: `gpg -d own/<date>.sql.gz.gpg | gunzip > restore.sql`, `psql "<empty project's DIRECT_URL>" -f restore.sql`, then `npx tsx prisma/apply-checks.ts` and `npm run db:check`. Its `keepalive` job re-enables `backup.yml` and `push-cron.yml` through the API each week, so GitHub's 60-day no-commit disable shouldn't hit either (if it ever does: Actions → workflow → Enable). A Last done item "Test a backup" (every 90 days, own DB) nudges a manual decrypt + look. The /settings JSON download is for reading, not restoring.

## Auth

One passcode (digits only, 4–8, entered on an iPhone-style keypad at `/login`; `src/components/LoginForm.tsx`), no accounts. Wrong tries are throttled in the `LoginThrottle` table (5 free, then 30 s doubling to 15 min; `src/lib/actions/auth.ts`). `src/proxy.ts` redirects every page without a valid signed cookie to `/login` (token logic in `src/lib/authToken.ts`, Web Crypto so it runs in the proxy). The proxy doesn't cover direct POSTs to server actions, so **every exported server action starts with `await requireAuth()`** (`src/lib/auth.ts`), and route handlers check `isAuthed()`. Add both to anything new.

## Prisma 7 specifics (important — differs from Prisma 5/6 patterns)

- Connection URLs are **not** in `prisma/schema.prisma`. They live in `prisma7.config.ts` (CLI commands) and are read directly from `process.env` in app code (runtime).
- `PrismaClient` requires an explicit driver adapter — there is no bare `new PrismaClient()`. See [src/lib/prisma.ts](src/lib/prisma.ts): a `pg.Pool` wrapped in `@prisma/adapter-pg`'s `PrismaPg`, passed as `{ adapter }`.
- Generated client output goes to `src/generated/prisma` (not `node_modules`), gitignored, regenerated via `postinstall`. Import from `@/generated/prisma/client`.
- The config file is named `prisma7.config.ts` (not `prisma.config.ts`) — this is Prisma's intentional convention for this major version, not a typo.

## Data model in one paragraph

A **month** is a `BudgetCycle` (calendar month, created automatically by `ensureMonthFor()`/`ensureCurrentMonth()` in `src/lib/data/ensureMonth.ts` when a date no month covers is needed — viewing a new month, or back-dating an expense into it — copying the previous one; skipped months are filled in, coverage is by date range so after an 18th→17th period the next month starts on the 18th; `startingBudget` = monthly budget, plus manual `bank`/`tricount`/`cash` balances and `rent`/`rentDay`). A **trip** is a `Trip`. Both hold `Expense` rows (`cycleId` or `tripId`, validated in `src/lib/actions/expenses.ts`). **Categories are one global list** (`Category`: name, color slot, sortOrder, isArchived, optional `pintPrice`), managed on the expenses page; there is no separate tag concept. Daily totals, cumulative-vs-budget, category/weekday stats, beer stats and the balance outlook are all **computed from expenses** in `src/lib/monthStats.ts` — nothing is stored per day. Pages that compare with history load it with `getPeriodSummaries()` (expenses summed per day × category in one `groupBy`) and only the shown period in full via `getPeriodData()`; summaries are right for totals/curves/categories, not for notes or beer counts. Deleting a category that has expenses is refused by the database (`onDelete: Restrict`); archive it instead. Trips can't overlap. A category with a `pintPrice` counts as beer. `BudgetCycle.label` ("Thuis", "Galway") groups periods; Insights compares a period with the average of the other *finished* periods with the same label, by day of the period (`src/lib/insights.ts`). New months inherit the previous label. `BudgetCycleDay` is legacy and unused. `SavingsEntry` and `Debt` are still display-only (no entry UI). **Subscriptions** (`Subscription`: name unique, `amount` = current price, category, `repeat` "monthly" | "yearly", `anchorDay` (+ `anchorMonth` yearly, both taken from the "next charge" date in the form; 29–31 clamp), `nextDueOn`, `isActive`; CHECK `subscription_valid`) are never logged by themselves: from `nextDueOn` they show on Budget Today, the hub tile and the morning digest; **Log** creates a normal Expense (counts against the budget like any other, `note` = name, `subscriptionId` set) **dated `nextDueOn`, not the tap day**, in the month covering it (`monthFor()` in `ensureMonth.ts`, also used by `createExpense`), and moves `nextDueOn` one renewal on; Skip only moves it. Missed renewals are not collapsed: each shows until logged or skipped. The move is guarded on the shown `nextDueOn` (double taps/other devices are no-ops). Logging another amount updates the price; the charge history is its expenses. Resuming a stopped one jumps to the first renewal ≥ today. Deleting keeps its expenses (`onDelete: SetNull`). **Recipes**: the Cookbook is `MyRecipe` rows (hand-written; ingredients and steps are plain `String[]` lines, `lastMadeOn`), the page Recipes opens on so a visit costs no quota. A right swipe stores a full snapshot in `SavedRecipe` (keyed by `spoonacularId`, `madeOn` null = still to make), so the saved list and detail pages never call the API. The Fridge tab searches Spoonacular `findByIngredients` with the `PantryItem` list only when "Find recipes" is pressed (`searchFridge` action) (`ignorePantry`, so basics never count as missing); adding ingredients suggests from `COMMON_INGREDIENTS` (`src/lib/recipes/ingredients.ts`, also the quick-add chips) plus saved-recipe ingredient names; that call and `/information` use `next.revalidate: 3600`, so repeats are free. Pages must never call Spoonacular while rendering: revalidating server actions re-render the current page, which would spend quota on every save (the deck and Fridge both fetch from the client). Left swipes aren't stored; the deck only skips saved recipes and those already shown in the current visit.

**Lessons** is unrelated to budget periods. A `StudyPeriod` is one semester: `startDate` (Monday of lesson week 1), `blokStart`, `endDate` (= last exam), `goalHours`/`topDayHours`. It has `StudyCourse`s (one `name`, unique per period, shown everywhere, palette `color`, `hasWc` adds a WC column to the grid), `StudyEntry` rows (date, hours, optional course, note; logging several courses at once splits the hours equally into one row per course; a 0 h row with a note = day off), `StudyExam`s (exam/test/deadline per course, optional note) and `LessonMark`s (grid cell course × week × HC/WC, statuses in `src/lib/lessons/marks.ts`). The **study timer** is one `StudyTimer` row (id "current", period, `courseIds`, `startedAt`; kept in the DB so any device can stop it); stopping saves its time through the same split as the form, dated the day it started, and deletes the row. While it runs the starting device shows a plain notification (`src/lib/lessons/timerNotification.ts`, via the service worker, Home Screen app only; iOS gives web apps no Live Activities / Dynamic Island), and `sw.js` opens Log time when it's tapped. Everything else is computed in `src/lib/lessons/stats.ts`. Pages load via `loadStudyPeriods()` (`src/lib/data/lessons.ts`): only the shown period in full, the others as headers (plus date/hours entries when comparing). New periods must start on a Monday. Periods are compared **counting down to their last exam** (same days-left). The semesters imported from the spreadsheets started logging at different points, so in comparisons the days before an imported period's first log are **filled in** with the hours of the most recent other period that logged that day, never the one being viewed (like the old "Vergelijking" sheets). Semesters logged in the app (start ≥ `LOGGED_IN_APP_FROM`, 3.1 on) are never filled in: an unlogged day is 0 h, so starting earlier shows as ahead and studying without logging needs back-dated entries. The period being viewed starts at 0 on its first log; the chart draws those parts dashed, and the average leaves out periods that are still all filled in at that point. Totals/KPIs never include filled-in hours.

**Reminders** are a `Reminder` row: `repeat` "once" | "daily" | "weekly" | "monthly" (the form's Daily/Weekly/Monthly toggles; none = once), `dueOn` (null = undated one-off), `weekdays` (weekly; `getUTCDay` numbers, 0 = Sunday), `anchorDay` (monthly; 29–31 clamp to the month's last day). Open = not done and `dueOn` null or ≤ today; the hub tile shows the open count. Ticking (`completeReminder`) sets `doneAt` on a one-off and moves a recurring one to its first date after today (`nextDueAfter`, missed ones don't pile up); undo restores the previous `dueOn`. **Last done** items are `Routine` rows (unique `name`, optional `everyDays` nudge) with one `RoutineLog` per day done (`@@unique([routineId, doneOn])`); "last done" is the newest log, never stored. Tapping the sheep logs today (again = take today off). Past `everyDays` they turn red and also appear in To do and the hub count.

**Beer** is built on Budget's expenses: a beer is an `Expense` in a category with a `pintPrice`, optionally with `pubId` (`Pub`: name, `latitude`/`longitude` both or neither = CHECK `pub_location`, `osmId` unique; `onDelete: SetNull`) and `pints` (1–50, CHECK `expense_pints`; null = guessed). `pintsOf()` in `monthStats.ts` is the one pint rule (counted, else `guessPints` = amount ÷ price, under `MIN_PINT_AMOUNT` = food), used by Budget and /beer alike; prices per pint only use counted beers. On Add expense a beer category shows `PubPicker`: **Nearby** asks GPS only on that tap, shows your pubs within 150 m first, then OpenStreetMap pubs/bars from Overpass, fetched **from the browser** (`src/lib/beer/nearby.ts`: main server 2.5 s then a mirror, 4 s total; the public servers are meant for human-operated tools, and are often busy, so a failure just means "type the name"). Typing suggests your pubs; a new name becomes a pub on save (with the fix if < 10 min old). The pints stepper starts at the guess from the pub's last price, else the category's, and that number is saved. The choice goes as JSON in the form's `pub` field (`parsePubChoice`), and in the offline outbox entry; `resolvePub` in `expenses.ts` matches by id, `osmId`, then case-insensitive name. Pages load everything via `getBeerVisits()` (`src/lib/data/beer.ts`).

**Waypoint** (merged in from a standalone app, history included; old notes in `docs/waypoint.md`) is unrelated to budget trips: `WaypointTrip` (UUID id, dates, `totalKm`, `routePreference`, whole-trip OSRM `routeGeometry` JSON) has ordered `WaypointLocation` stops (`visitOrder`). Its components still speak the old snake_case Supabase shapes (`src/lib/waypoint/types.ts`); `src/lib/waypoint/rows.ts` maps Prisma rows to them. Server pages read via `src/lib/data/waypoint.ts`; interactive pages get their initial data from the server page and mutate through `src/lib/actions/waypoint.ts`. The route (km + line) is recalculated on the server from the stored stops (`recalculateTripRoute`), only when the stop order changes; overview maps pass `getAllTrips({ simplify })` to thin the lines (`src/lib/waypoint/simplify.ts`).

## Gotchas

- **Push notifications**: `.github/workflows/push-cron.yml` calls `/api/push/cron` every 15 minutes (at :02/:17/:32/:47, GitHub is most late on the hour); `runPushSchedule()` (`src/lib/push/schedule.ts`) checks each `PushSubscription` (one per device: endpoint/keys, `timeZone`, enabled `kinds`) against its window in that device's local time: from the time picked per kind on /settings (`PushSubscription.times` JSON `{kind: "HH:MM"}`, only non-defaults stored; defaults in `kinds.ts`: digest 8:00, study goal 20:00, expenses 21:00, Sunday review 19:00) for `WINDOW_HOURS` (3, Sunday review 4), never past midnight (digest, study goal, expenses, Sunday review = Mon–Sun spend vs each day's share of the running budget, study vs goal minus days off, Last done, subscriptions logged; forgotten timer after 3 h) and records `PushSent` keys (`<sub>:<kind>:<day>`) so each goes out once (/settings shows each kind's newest one as "Last sent"); failed sends un-claim and retry, 404/410 deletes the device. Nothing is sent when there's nothing to say, except the digest, which goes out every morning ("Nothing on the list today." when empty). **Weather**: a device with a location (`PushSubscription.latitude`/`longitude`/`placeLabel`/`locationSource` "gps" | "city"/`locationAt`, all-or-nothing CHECK `push_location`, set on /settings via `setWeatherLocation`) gets one Open-Meteo line on top of its digest (`src/lib/push/weather.ts`: thresholds as constants, 3 s timeout, coordinates rounded to 0.1° so nearby devices share a cached forecast); a failed forecast just leaves it out. The same line shows under the greeting on Home: `HomeWeather` finds this device's push endpoint and asks `GET /api/weather?endpoint=` (nothing shown without a subscription + location). GPS place names come from Nominatim reverse (Open-Meteo has none); city search calls Open-Meteo geocoding from the browser. `LocationSync` (root layout) refreshes a "gps" location on app open at most every 3 h, only when geolocation is already granted (never prompts) and never over a picked city. `public/sw.js` shows the `push` and opens `data.url` on tap. iOS: Home Screen app only (16.4+). Add a new kind in `kinds.ts` + `schedule.ts` (+ its window in `window.ts`, the pure timing helpers: `isKindDueNow`, `weekBudget`, `rentDateIn`, tested in `window.test.ts`).

- **Supabase API is shut out**: the `anon`/`authenticated` roles have no grants on `public` (also by default for new tables) and every table has RLS on with no policies. The app connects as `postgres` (owner, bypasses RLS) so it's unaffected. `apply-checks.ts` re-applies both first thing; never add RLS policies or grants unless a feature really uses Supabase's API.
- After `prisma generate`/`db:push` changes, **restart `npm run dev`** — the running server keeps the old generated client in memory.
- Date-only columns are UTC midnight; use `dayKey()`/`toDateInputValue()` from `src/lib/format.ts` rather than `toISOString()` slices scattered around.
- Amount inputs go through `parseAmount()`, which evaluates calculations with `+ − × ÷` (`6,8+7,4`, `12,50×3`; × ÷ first, trailing operator ignored). On /budget/add the one `+` button opens the operator picker and the total shows inside the amount box.
- **Offline**: `public/sw.js` (registered in production only by `ServiceWorkerRegister`) keeps only `/budget/add` plus `/_next/static` chunks. In-app taps are client-side navigations the worker never sees, so every page load posts `cache-offline-pages` and the worker fetches `/budget/add` itself (at most every 15 min) along with the chunks named in its HTML; every other page offline shows the self-contained `public/offline.html`. Expenses saved offline go into a localStorage queue (`src/lib/offline/outbox.ts`, listed by `PendingExpenses`) and are sent by `OutboxSync` (root layout) on load / `online` / reopen. The entry's UUID is passed as `clientId` and becomes the `Expense.id`, so retries never duplicate. A send that throws while the phone says it's online (logged out, server down, an offline copy from an older build) sets a sync-failed flag and `PendingExpenses` offers Reload. The worker only caches the plain `/budget/add` URL (never `?period=`) and re-puts that page's chunks on each refresh so the 300-entry prune never evicts them. Bump `VERSION` in `sw.js` when changing what it caches; `sw.js` and `offline.html` are excluded from the proxy.
- **"Today" on the server** comes from `getTodayKey()` / `getTimeZone()` in `src/lib/today.ts` (browser timezone via the `tz` cookie set by `TimeZoneSync`, fallback Europe/Brussels) — never `toDateInputValue()` server-side, Vercel runs in UTC.
- An expense's **date decides its month**: `createExpense`/`updateExpense` move it to the `BudgetCycle` that covers the date ("yesterday" on the 1st lands in last month); trips only accept dates inside the trip.
- Pages that read the DB without searchParams/cookies need `await connection()` or they get prerendered at build time.
- **Speed**: `vercel.json` pins functions to `lhr1` (London), next to Supabase `eu-west-2` — every query was a transatlantic round trip from the default US region. `next.config.ts` sets `staleTimes.dynamic: 60`, so revisiting a page within a minute is served from the client router cache; that's why **every mutating server action must call `revalidatePath`** (any call clears that cache). Data changed elsewhere can look ≤60 s old until a reload.
- **Waypoint styling** uses the same Meadow tokens as Budget (no separate palette). Its shadcn-style UI (`src/components/waypoint/ui`) reads the aliases `card`, `muted`, `muted-foreground`, `popover`, `secondary`, `destructive`, `input` and `ring` that `globals.css` maps onto Meadow. `accent` is NOT an alias (it is Meadow's grass green for charts), so Waypoint hover states use `bg-surface-muted`. `src/app/waypoint/layout.tsx` renders `data-waypoint`, which only widens the root `<main>`.
- **Waypoint image export on iOS** (`src/lib/waypoint/useImageExport.ts`): render and save are two separate taps, the image is a Blob (never a `data:` URL), and nothing may be `await`ed before `navigator.share`. Maps that get captured need `preserveDrawingBuffer` (opt-in prop). The public OSRM server ignores `avoid_tolls`.

## Mobile-first conventions

- Phones are the primary target (~375px). Budget pages get a fixed bottom tab bar (`src/components/budget/BudgetTabBar.tsx`, hidden from `sm:`); its height is cleared by the `.pb-tabbar` utility in `globals.css`. Respect `env(safe-area-inset-*)`.
- Inputs are forced to 16px below `sm` in `globals.css` (prevents iOS focus-zoom) — don't fight it with per-input sizes.
- **Buttons** use the shared utilities in `globals.css`: `btn` (pill shape, hover tint, tap tint + press-in, focus ring, disabled) plus one colour — `btn-primary`, `btn-outline`, `btn-danger`, `btn-destructive`, `btn-ghost` (text links too). Tappable rows/cards use `tap`. Waypoint's `Button`/`buttonVariants` are built on the same classes; don't hand-roll button colours or `rounded-lg` buttons.
- Tap targets ≥ 44px (`min-h-11` / `h-11 w-11`); Waypoint's `Button` sizes are 44px on phones. Hover-only controls are revealed with `[@media(hover:hover)]:opacity-0`, never plain `opacity-0 group-hover:`.
- **No scroll traps**: embedded MapLibre maps use `cooperativeGestures` on touch (one finger scrolls the page; off only on the full-screen map page); a two-axis table scrolls inside one fixed-height box so sticky header + column both work (`LessonGrid`); `body` has `overflow-x: clip`.
- **Insights stay calm**: headline + one chart + categories/courses visible; deeper cuts and long history lists go in `Disclosure` (`src/components/Disclosure.tsx`), long lists show the latest few with "Show all".
- PWA: `src/app/manifest.ts`, icons in `public/` (`icon-*.png`, `apple-icon.png`, `favicon.ico`, generated from `public/icon.svg` with sharp), linked per theme via `THEME_ICONS` in `src/lib/theme.ts` (not the `src/app` file convention, which would override it).
